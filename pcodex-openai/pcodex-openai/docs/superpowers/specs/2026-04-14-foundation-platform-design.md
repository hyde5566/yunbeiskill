# 云贝Skill管理系统第一阶段基础平台设计

## 1. 文档目标

本文档用于定义云贝Skill管理系统第一阶段的实现设计，作为后续实施计划和开发落地的唯一设计基线。

本设计严格遵循以下约束：

- 仅参考需求文档 `D:\Project\yunbeiskill\docs\云贝Skill管理系统-需求文档.md`
- 系统为全新构建
- 新系统代码与配套文档均落在 `D:\Project\yunbeiskill\pcodex-openai`
- 不复用、不修改旧版本代码

## 2. 第一阶段目标

第一阶段不直接进入 Skill 提交、审核、发布、检索、下载等业务闭环，而是先完成后续所有业务依赖的基础平台。

第一阶段目标：

- 搭建单仓全栈项目骨架
- 完成统一登录与会话认证
- 完成角色驱动的功能权限体系
- 完成用户、角色、部门、项目、Skill 分类管理
- 完成登录日志与操作日志
- 形成统一单端应用框架，为后续 Skill 业务模块直接接入提供稳定底座

## 3. 范围定义

### 3.1 本期纳入范围

- 账号密码登录
- 当前用户信息获取
- 修改本人密码
- 用户管理
- 角色管理
- 功能权限点管理
- 部门管理
- 项目管理
- 项目成员管理
- Skill 分类管理
- 登录日志查询
- 操作日志查询
- 单端应用壳子、动态菜单、权限路由控制
- 基础通知中心页面占位

### 3.2 本期明确不做

- Skill 提交
- Skill 审核
- Skill 发布
- Skill 检索中心
- Skill 下载与版本管理
- Skill 评分反馈
- 批量导入
- 文件导出
- 自动化通知触发流程
- 部门数据权限
- 通用细粒度数据权限引擎

### 3.3 与后续阶段的接口边界

第一阶段虽然不实现 Skill 主流程，但需要为后续能力预留挂接点：

- Skill 未来会关联分类、项目、提交人、审核人、发布人
- Skill 可见范围未来单独按业务规则实现，不并入后台通用数据权限
- 通知、日志、权限点设计需支持后续 Skill 模块复用

## 4. 总体架构

### 4.1 技术选型

- 前端：Vue 3
- 后端：NestJS
- 数据库：MySQL
- 鉴权：JWT

### 4.2 仓库结构

建议在 `D:\Project\yunbeiskill\pcodex-openai` 下采用单仓结构：

```text
pcodex-openai/
  apps/
    web/
    api/
  packages/
    shared/
  docs/
    superpowers/
      specs/
      plans/
```

职责划分：

- `apps/web`：单端应用前端，实现登录后统一工作台、动态菜单和管理页面
- `apps/api`：后端服务，负责认证、权限、基础资料、日志
- `packages/shared`：共享类型、枚举、权限点定义、通用常量

### 4.3 单端应用原则

系统为一套单端应用，管理员与员工共用同一个前端框架，不拆为两个系统。

差异化通过权限实现：

- 登录后统一进入同一套主布局
- 菜单、按钮、页面访问能力按角色权限动态控制
- 员工与管理员共用公共页面
- 管理型页面仅在具备对应功能权限时显示和可访问

## 5. 权限设计

### 5.1 设计原则

- 权限与角色挂钩，不直接挂账号
- 角色为完全自定义
- 一个账号可拥有多个角色
- 一个角色可拥有多个功能权限点
- 账号最终权限取所有角色权限并集
- 部门仅为组织关系属性，不参与权限判断

### 5.2 功能权限模型

功能权限按“模块 -> 功能点”拆解，由角色进行勾选配置。

第一阶段权限点分组建议如下。

#### 用户与角色

- `user.view`
- `user.create`
- `user.edit`
- `user.enable-disable`
- `user.assign-role`
- `role.view`
- `role.create`
- `role.edit`
- `role.delete`

#### 部门管理

- `department.view`
- `department.create`
- `department.edit`
- `department.delete`
- `department.member.view`

#### 项目管理

- `project.view`
- `project.create`
- `project.edit`
- `project.delete`
- `project.member.view`
- `project.member.add`
- `project.member.remove`

#### Skill 分类管理

- `skill-category.view`
- `skill-category.edit`
- `skill-category.enable-disable`
- `skill-category.sort`

#### 日志管理

- `login-log.view`
- `operation-log.view`
- `log.export`

#### 系统公共能力

- `dashboard.view`
- `profile.view`
- `profile.edit`
- `notification.view`

### 5.3 数据权限模型

第一阶段不建设后台通用数据权限体系。

规则如下：

- 用户、角色、部门、项目、分类、日志等后台模块：只要角色具备对应功能权限，默认即可查看该模块全部数据
- 不提供部门范围、本人范围、本组范围等后台数据限制
- Skill 数据权限后续单独实现，不混入当前后台权限体系

### 5.4 Skill 可见范围的预留规则

虽然第一阶段不开发 Skill 模块，但后续必须保留以下独立业务规则：

- 全部可见
- 项目成员可见
- 指定账号可见

该规则是 Skill 实体自己的可见范围字段，不是角色数据权限。

## 6. 核心模块设计

### 6.1 认证模块

职责：

- 账号密码登录
- JWT 签发与校验
- 当前登录用户信息返回
- 修改本人密码
- 退出登录

关键规则：

- 仅启用状态账号可登录
- 登录失败也记录日志
- 停用账号后，已有会话在后续校验时失效

### 6.2 用户管理模块

职责：

- 用户列表查询
- 创建用户
- 编辑用户
- 停用/启用用户
- 分配角色

关键规则：

- 每个用户必须归属一个部门
- 用户可被分配多个角色
- 账号唯一
- 停用优先于物理删除

### 6.3 角色管理模块

职责：

- 自定义角色创建、编辑、删除
- 为角色勾选功能权限点
- 供用户分配角色时选择

关键规则：

- 角色编码唯一
- 已分配给用户的角色不允许直接硬删除，优先停用或要求先解除绑定

### 6.4 部门管理模块

职责：

- 维护多层级部门结构
- 查看部门成员
- 为用户提供组织归属

关键规则：

- 支持父子级树形结构
- 有成员的部门不可直接删除
- 部门不参与数据权限判断

### 6.5 项目管理模块

职责：

- 项目列表维护
- 项目增删改查
- 项目成员添加与移除

关键规则：

- 一个项目可有多个成员
- 一个用户可加入多个项目
- 第一阶段不做批量导入
- 后续 Skill 模块将从项目列表中选择关联项目

### 6.6 Skill 分类管理模块

职责：

- 展示和维护 Skill 分类
- 为后续 Skill 提交和检索提供基础字典

关键规则：

- 第一阶段初始化 7 个预设分类
- 支持排序和启停用
- 后续 Skill 记录将关联分类

### 6.7 日志模块

分为两类：

- 登录日志
- 操作日志

登录日志记录：

- 登录账号
- 用户ID
- 登录时间
- 登录IP
- 登录状态
- 失败原因

操作日志记录：

- 操作人
- 操作时间
- 模块
- 操作类型
- 对象类型
- 对象ID
- 操作详情

第一阶段操作日志重点覆盖：

- 用户创建、修改、停用、角色分配
- 角色创建、修改、删除
- 部门创建、修改、删除
- 项目创建、修改、删除、成员变更
- 分类编辑、启停用、排序

## 10. 数据流与关键交互

### 10.1 登录流程

```text
用户提交账号密码
-> 后端校验账号状态与密码
-> 记录登录日志
-> 成功则签发 JWT
-> 前端保存登录态并拉取当前用户信息
-> 前端按角色汇总权限后渲染菜单
```

### 10.2 管理页面访问流程

```text
前端根据当前用户权限渲染菜单与按钮
-> 用户访问页面或触发操作
-> 后端守卫校验 JWT
-> 后端权限守卫校验功能权限点
-> 成功返回数据
-> 关键写操作记录操作日志
```

### 10.3 项目成员维护流程

```text
管理员进入项目详情
-> 查看当前成员列表
-> 选择用户添加或移除
-> 后端更新 project_members
-> 记录操作日志
```

## 11. 错误处理设计

统一错误处理原则：

- 未登录：返回认证失效，前端跳转登录页
- 无权限：返回明确权限不足提示
- 业务校验失败：返回明确业务错误信息
- 系统异常：统一兜底提示，避免暴露内部实现细节

典型业务错误包括：

- 账号已存在
- 角色编码重复
- 部门下仍有成员不可删除
- 项目不存在
- 项目成员重复添加
- 分类编码重复

## 15. 风险与约束

### 15.1 主要风险

- 角色与权限点命名若不稳定，后续扩展 Skill 模块时容易重复或冲突
- 若前端只做菜单隐藏而后端未做权限校验，会造成越权风险
- 若操作日志在各业务模块中手工拼装，后期维护成本会升高

### 15.2 控制策略

- 权限点统一集中定义，前后端共享
- 后端统一守卫校验权限
- 操作日志通过统一拦截或公共服务记录
- 第一阶段严格控制范围，不提前实现 Skill 主流程

## 16. 设计结论

第一阶段采用“单仓全栈基础平台先行”方案是合理的。

该方案满足以下目标：

- 符合单端应用要求
- 满足角色驱动的功能权限体系
- 不错误引入部门数据权限
- 为后续 Skill 模块提供稳定的用户、角色、项目、分类、日志基础
- 范围清晰，可直接进入实施计划编写阶段
