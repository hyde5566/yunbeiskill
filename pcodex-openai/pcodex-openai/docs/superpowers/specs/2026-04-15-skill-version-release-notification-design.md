# Skill 新版本发布通知设计

## 背景

需求文档明确要求：

- Skill 新版本发布后，系统向已下载该 Skill 的员工发送站内通知
- 通知触达方式仅为站内通知
- 第一版通知中心至少支持通知列表、通知详情、标记已读

当前系统现状：

- Skill 提交、审核、发布、版本管理、下载记录、评分反馈已经完成
- 前端通知中心仍为占位页
- 后端尚未建立通知数据表与通知接口

因此这一轮只实现“新版本发布通知已下载用户”的最小闭环，不同时引入系统公告、审核分配通知、批量已读、删除通知等扩展范围。

## 目标

本轮交付后，系统需要支持：

1. 已发布 Skill 的新版本再次发布成功后，自动为已下载该 Skill 系列的用户生成站内通知
2. 员工可在通知中心查看自己的通知列表和通知详情
3. 员工可将通知标记为已读
4. 通知内容能明确说明 Skill 名称、新版本号、更新说明摘要，并支持跳转到对应 Skill 详情页

## 非目标

本轮明确不做：

- 首次发布通知
- 审核分配通知
- 系统公告
- 通知删除
- 批量已读
- 未读角标
- 实时推送
- 通知模板配置页
- 通知频率汇总或合并策略

## 总体方案

采用“事件触发型站内通知”方案：

- 当已发布 Skill 的新版本完成发布时，在发布流程内同步生成通知
- 接收人来源于该 Skill 系列的下载记录
- 对接收人去重后，按用户逐条创建通知记录
- 通知中心从占位页升级为真实的列表 + 详情 + 标记已读页面

该方案与现有发布、下载记录、通知中心占位结构最匹配，且实现复杂度最低。

## 数据模型

新增 `notifications` 表，字段建议如下：

- `id`
- `user_id`
- `type`
- `title`
- `content`
- `is_read`
- `read_at`
- `created_at`
- `skill_series_id`
- `skill_id`
- `version_label`

字段说明：

- `type` 第一版仅支持 `SKILL_VERSION_RELEASED`
- `skill_series_id` 用于跳转到同一 Skill 系列
- `skill_id` 指向本次发布的具体版本
- `version_label` 便于前端直接展示
- `title` 和 `content` 直接落已渲染文本，第一版不做模板引擎

## 触发规则

通知只在以下条件同时满足时生成：

1. 当前发布动作对应的是“新版本发布”
2. 该 Skill 在发布前已经存在已发布版本
3. 当前发布成功

不触发通知的情况：

- 首次发布
- 审核通过但未发布
- 历史版本查看
- 评分、下载等其他动作

## 接收人规则

接收人通过 `skill_download_records` 获取：

- 查询与当前 `seriesId` 对应的全部下载记录
- 提取下载用户 `downloaderId`
- 按用户去重
- 仅为当前仍有效的用户创建通知

规则说明：

- 同一用户即使下载过多次，也只生成一条本次版本发布通知
- 从未下载过该 Skill 的用户不接收通知
- 不做部门范围或项目范围额外过滤，因为需求明确是“已下载用户”

## 通知内容

### 标题

`Skill 新版本已发布：{Skill名称} {版本号}`

### 正文

正文包含以下信息：

- Skill 名称
- 新版本号
- 更新说明摘要
- 提示前往详情页下载

更新说明摘要采用截断策略：

- 保存前 200 个字符
- 超出则追加省略号

## 后端接口

第一版接口仅包括：

### `GET /notifications`

返回当前用户通知列表。

支持简单筛选：

- `isRead=true`
- `isRead=false`

### `GET /notifications/:id`

返回当前用户单条通知详情。

要求：

- 只能查看自己的通知
- 若通知不存在或不属于当前用户，返回无权或不存在

### `PATCH /notifications/:id/read`

将当前用户通知标记为已读。

要求：

- 幂等
- 重复标记不报错

## 权限规则

第一版不引入复杂通知权限点。

规则：

- 只要用户已登录，即可访问通知中心
- 只能访问自己的通知
- 不提供通知后台管理页

## 前端设计

当前通知中心页面：

- [NotificationPage.vue](D:/Project/yunbeiskill/.worktrees/foundation-platform/pcodex-openai/apps/web/src/pages/notifications/NotificationPage.vue)

需要升级为真实通知页面，结构如下：

### 通知列表

展示：

- 标题
- 创建时间
- 已读/未读状态
- 摘要

### 通知详情

点击列表项后展示详情，包括：

- 标题
- 发布时间
- 完整正文
- 关联的 Skill 名称和版本号
- 跳转到 Skill 详情页按钮

### 标记已读

- 提供显式“标记已读”按钮
- 第一版不自动在打开详情时已读

## 与现有流程的衔接

通知生成逻辑挂在 Skill 发布流程中。

建议做法：

- 在 Skill 发布成功后，判断当前是否为“新版本发布”
- 若是，则调用通知生成逻辑
- 若通知生成失败，发布流程整体应失败，避免“版本已发布但通知缺失”的半成功状态

## 错误处理

### 发布触发通知失败

- 返回失败
- 不保留“发布成功但通知未发”的不一致状态

### 用户读取通知失败

- 按常规返回不存在或无权限

### 标记已读失败

- 返回明确错误，前端提示“标记已读失败，请稍后重试”

## 测试策略

### 后端

至少覆盖：

- 新版本发布后生成通知
- 首次发布不生成通知
- 同一用户多次下载，仅生成一条通知
- 非下载用户不生成通知
- 当前用户只能查看自己的通知
- 标记已读幂等

### 前端

至少覆盖：

- 通知列表渲染
- 已读/未读状态显示
- 通知详情展示
- 标记已读后状态刷新
- 跳转 Skill 详情行为

## 风险与后续扩展

### 当前风险

- 通知生成放在发布事务链路中，会增加发布动作的写入成本，但当前规模可接受
- 若后续 Skill 更新频繁，通知可能过多；本轮不做频率合并

### 后续可扩展方向

- 审核分配通知
- 系统公告
- 批量已读
- 通知删除
- 未读数量角标
- 模板配置与频率控制

## 验收标准

满足以下条件即可视为本轮完成：

1. 已发布 Skill 的新版本再次发布后，已下载用户收到站内通知
2. 通知中心能查看通知列表
3. 通知详情能展示 Skill 名称、版本号、更新说明摘要
4. 用户能标记已读
5. 用户可从通知跳转到对应 Skill 详情页
