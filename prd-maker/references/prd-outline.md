# PRD 结构参考

## 用途

本文件用于提供更贴近中文产品经理日常工作的 PRD 章节结构。

目标是让需求文档更适合拿去做内部评审、研发对齐、测试验收和业务确认。

## 使用原则

按以下顺序组织 PRD：

1. 先说清楚这是什么需求
2. 再说清楚为什么要做
3. 再说清楚目标是什么
4. 再说清楚谁来用、谁来管
5. 再说清楚本期做什么、不做什么
6. 再说清楚流程和功能
7. 再说清楚规则、校验、异常、权限
8. 最后说清楚怎么验收、有哪些风险

不要一开始直接写页面按钮和字段，而忽略背景、目标和范围。

## 推荐 PRD 结构

### 0. 文档信息（按需）

建议包含：

- 文档名称
- 版本号
- 作者
- 更新时间
- 评审人
- 所属项目 / 业务线
- 原型链接 / 需求链接

适用场景：

- 正式评审稿
- 需要版本管理的长期文档
- 需要多人协作的需求文档

### 1. 需求概述

先用简洁语言说明：

- 本次需求是什么
- 核心解决什么问题
- 涉及哪些角色
- 预期产出是什么

建议控制在 3-5 句话，方便业务、研发、测试快速建立上下文。

### 2. 需求背景

重点说明：

- 当前现状是什么
- 存在哪些痛点或效率问题
- 为什么现在要做
- 不做会有什么影响

可选写法：

- 业务背景
- 用户痛点
- 现有方案不足
- 数据表现 / 案例佐证

### 3. 需求目标

重点说明：

- 这次需求希望达成什么结果
- 是提升效率、提升转化、减少投诉，还是补齐流程能力
- 是否有明确指标

建议区分：

- 业务目标
- 用户目标
- 系统目标

### 4. 术语说明（按需）

当文档中存在业务缩写、专业术语、状态名、角色名时，建议增加本节。

示例：

- ERP：企业资源计划系统
- 调度单：系统内用于分配任务的业务单据
- 初审：贷款流程中的第一轮审核状态

### 5. 角色说明

建议按角色逐一说明：

- 角色名称
- 角色职责
- 可见范围
- 可操作范围
- 数据权限范围

典型角色：

- 超级管理员
- 运营
- 审核员
- 业务经理
- 普通用户
- 第三方合作方

不要把所有权限混写成“用户可操作”。

### 6. 范围说明

建议拆为：

- 本期范围
- 非本期范围
- 后续规划（按需）

目的：

- 防止需求失控
- 降低评审误解
- 帮助研发判断当前交付边界

### 7. 业务流程

建议写清：

- 谁发起
- 谁处理
- 系统做什么
- 数据如何流转
- 状态如何变化
- 结束条件是什么

流程较复杂时建议拆为：

- 主流程
- 分支流程
- 异常流程

如果是改造型需求，建议区分：

- 现状流程
- 目标流程

### 8. 功能结构 / 功能清单

建议先总后分：

- 一级模块
- 二级模块
- 页面或子功能
- 关键动作

示例：

- 用户管理
  - 用户列表
  - 新建用户
  - 编辑用户
  - 禁用用户

目的：

- 便于评审快速看到范围
- 便于研发拆任务
- 便于测试拆用例

### 9. 模块说明 / 页面说明

每个模块或页面建议说明：

- 名称
- 目标
- 使用角色
- 入口路径
- 前置条件
- 主要内容
- 主要操作
- 操作结果

如果页面很多，先写模块摘要，再逐页展开。

### 10. 字段与交互说明

建议说明：

- 字段名称
- 业务含义
- 字段类型
- 是否必填
- 默认值
- 是否可编辑
- 展示规则
- 联动关系
- 提示文案

交互方面建议说明：

- 点击后发生什么
- 是否弹窗 / 跳转 / 局部刷新
- 成功提示是什么
- 失败提示是什么
- 禁用态是什么

### 11. 业务规则

建议覆盖：

- 状态流转规则
- 创建规则
- 编辑规则
- 删除规则
- 分配规则
- 计算规则
- 排序规则
- 限制规则
- 时效规则
- 导入导出规则
- 批量操作规则

业务规则不要只写“按现有逻辑处理”，应尽量明确到可执行层面。

### 12. 校验规则

建议覆盖：

- 必填校验
- 格式校验
- 长度校验
- 范围校验
- 唯一性校验
- 跨字段校验
- 附件校验
- 时间校验
- 条件校验

能明确报错提示的，优先补齐提示文案。

### 13. 异常场景

建议覆盖：

- 无数据
- 无权限
- 状态不允许
- 重复提交
- 数据已失效
- 外部接口失败
- 并发冲突
- 部分成功
- 超时释放
- 重试与回滚

每个异常建议说明：

- 触发条件
- 系统处理
- 用户提示
- 是否允许继续操作

### 14. 权限说明

建议区分：

- 页面权限
- 按钮权限
- 数据权限
- 特殊角色限制

常见写法：

- 总部用户可查看全部数据
- 分公司用户仅可查看本公司数据
- 审核通过后不可编辑
- 无导出权限时不展示导出按钮

### 15. 数据统计 / 埋点 / 报表

按需说明：

- 需要统计哪些指标
- 埋点事件是什么
- 操作日志记录什么
- 导出包含哪些字段
- 报表按什么维度统计
- 时间口径如何定义

如果需求涉及运营分析、效率统计、过程留痕，这一节不要省略。

### 16. 验收标准

建议对每个核心功能说明：

- 前置条件
- 操作步骤
- 预期结果
- 异常结果

好的验收标准应满足：

- 可测试
- 可观察
- 不歧义
- 与业务规则一致

### 17. 依赖与排期（按需）

在这些场景建议增加本节：

- 依赖接口或第三方系统
- 需要多团队协作
- 有明确上线时间或灰度计划
- 需要区分一期、二期

可包含：

- 上下游依赖
- 资源依赖
- 里程碑
- 风险缓冲
- 灰度策略

### 18. 风险与待确认项

统一收口：

- 未确认规则
- 待业务拍板事项
- 接口待确认项
- 历史数据处理方式
- 合规风险
- 上线风险

不要让不确定信息散落在各章节里。

## 推荐输出层级

### 简版

适用于快速讨论、需求雏形阶段。

建议包含：

- 需求概述
- 背景与目标
- 功能清单
- 核心规则
- 待确认项

### 标准版

默认使用。

建议包含：

- 从“需求概述”到“风险与待确认项”的完整主干
- 重点模块的页面级说明
- 足够支撑研发评审和测试理解的规则内容

### 详细版

适用于正式评审稿或交付稿。

建议包含：

- 文档信息 / 版本记录
- 完整业务流程
- 页面级细节
- 字段级规则
- 校验和异常
- 权限差异
- 验收标准
- 依赖与排期

## 写作建议

- 章节名称尽量稳定
- 术语、状态、按钮名称要统一
- 背景、目标、方案、规则分开写
- 现状与目标分开写
- 正常流程与异常流程分开写
- 尽量使用编号和清单，而不是大段叙述
- 让业务、产品、设计、研发、测试都能读懂

## 最低完整度要求

至少应包含：

- 需求概述
- 背景
- 目标
- 角色
- 范围
- 主要流程
- 功能清单
- 核心规则
- 基础校验
- 基础异常
- 权限说明
- 验收标准
- 待确认项

## 最后提醒

一份好的 PRD 不只是“功能说明书”，还应当明确边界、规则、异常、权限和验收方式。
