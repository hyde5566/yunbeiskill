# PRD 评审与补漏清单

## 用途

用于检查一份 PRD 是否已经达到中文产品团队常见的“可评审、可开发、可测试、可落地”标准。

适用场景：

- 写新 PRD 时自检
- 补全文档时查漏补缺
- 评审别人的 PRD
- 评审会前做快速走查
- 研发、测试反馈“文档不清楚”时反查问题点

## 总体判断标准

一份 PRD 不是写得长就算完整。

真正完整的标准是：

- 业务方看得懂为什么做
- 产品看得懂边界和规则
- 设计看得懂页面目标和交互要求
- 研发看得懂要做什么和不能做什么
- 测试看得懂怎么验收

## 评审维度

从以下维度评审：

1. 需求概述是否清楚
2. 背景是否成立
3. 目标是否明确
4. 角色是否清楚
5. 范围是否清楚
6. 流程是否完整
7. 功能是否覆盖完整
8. 页面说明是否清楚
9. 字段是否定义清楚
10. 业务规则是否明确
11. 校验规则是否明确
12. 异常场景是否覆盖
13. 权限是否完整
14. 数据/日志/报表是否说明
15. 验收是否可测
16. 风险和待确认项是否收口

## 1. 需求概述检查

检查是否说明：

- 这次需求到底是什么
- 解决什么问题
- 涉及哪些角色
- 交付的大致范围是什么

常见问题：

- 一上来直接写页面功能，没有一句话概述
- 描述太技术化，业务方看不懂
- 看完不知道这个需求的核心目标是什么

## 2. 背景检查

检查是否说明：

- 当前现状是什么
- 痛点是什么
- 为什么现在做
- 不做有什么影响

常见问题：

- 只有功能，没有背景
- 只有结论，没有现状问题
- 背景不成立，像是为了做功能而做功能

## 3. 目标检查

检查是否说明：

- 这次想达成什么结果
- 是效率提升、转化提升、流程补齐还是风险控制
- 是否有可量化指标或明确结果

常见问题：

- 把功能清单当目标
- 目标和背景不对应
- 没有成功判断标准

## 4. 角色检查

检查是否明确：

- 有哪些角色
- 各角色职责是什么
- 各角色可看什么
- 各角色可操作什么
- 是否有数据范围差异

常见问题：

- 全部写成“用户”
- 角色权限混在一起
- 缺少总部 / 分公司 / 管理员 / 审核员等差异

## 5. 范围检查

检查是否明确：

- 本期做什么
- 本期不做什么
- 哪些属于后续规划
- 哪些依赖其他团队或系统

常见问题：

- 边界不清，评审时大家理解不同
- 把未来规划混进当前范围
- 研发无法判断本期交付边界

## 6. 流程检查

检查是否写清：

- 谁发起
- 谁处理
- 谁审批 / 确认
- 系统在各环节做什么
- 数据或状态如何变化
- 流程何时结束

复杂场景再检查：

- 是否有主流程
- 是否有分支流程
- 是否有异常流程
- 是否区分现状流程和目标流程

常见问题：

- 只有模块列表，没有业务流程
- 状态变化不清
- 看不出责任人和流转顺序

## 7. 功能清单检查

检查是否具备：

- 模块拆分完整
- 子功能拆分合理
- 页面入口清晰
- 支撑主流程的辅助功能没有缺失

常见问题：

- 功能点写得很散
- 没有层级关系
- 主流程能跑，但配套能力缺失，如查询、导出、日志、权限配置

## 8. 页面说明检查

检查重要页面是否写清：

- 页面目标
- 使用角色
- 入口路径
- 页面组成
- 主要操作
- 操作后结果

常见问题：

- 只列页面名，不写页面作用
- 操作行为有了，但结果没写
- 前置条件缺失

## 9. 字段检查

检查关键字段是否明确：

- 字段名称
- 业务含义
- 字段类型
- 是否必填
- 默认值
- 是否可编辑
- 展示规则
- 选项来源
- 联动关系
- 错误提示

常见问题：

- 字段只出现名称，没有定义
- 下拉项来源不明
- 可编辑条件不明
- 缺少提示文案

## 10. 业务规则检查

检查是否覆盖：

- 状态流转
- 创建条件
- 编辑条件
- 删除条件
- 启停条件
- 分配规则
- 计算规则
- 排序规则
- 超时 / SLA
- 批量操作
- 导入导出
- 日志留痕
- 历史数据处理

常见问题：

- 只写正常路径
- 默认“按现有逻辑处理”
- 不同章节之间规则冲突

## 11. 校验规则检查

检查是否覆盖：

- 必填校验
- 格式校验
- 长度校验
- 范围校验
- 唯一性校验
- 条件校验
- 跨字段校验
- 时间校验
- 附件校验

常见问题：

- 写“需校验”但没写怎么校验
- 没有报错提示文案
- 条件校验缺失

## 12. 异常场景检查

检查是否覆盖：

- 无数据
- 无权限
- 状态不允许
- 重复提交
- 数据失效
- 接口失败
- 并发冲突
- 超时
- 部分成功
- 回滚 / 重试

常见问题：

- 只有正常流程
- 失败后系统怎么处理没写
- 用户提示不明确
- 异常责任边界不清

## 13. 权限检查

检查是否区分：

- 页面权限
- 按钮权限
- 数据权限
- 特殊角色限制
- 状态变化后的权限变化

常见问题：

- 页面能看不代表按钮能点，但文档没区分
- 可操作权限和数据可见权限混写
- 缺少组织/区域/部门数据范围说明

## 14. 数据 / 埋点 / 报表检查

检查是否说明：

- 要统计哪些指标
- 是否需要操作日志
- 是否要支持导出
- 导出范围是否继承筛选条件
- 报表维度和时间口径是什么
- 埋点事件和关键字段是什么

常见问题：

- 只写“支持统计”
- 指标口径不清
- 导出字段、范围、上限没写

## 15. 验收检查

检查验收标准是否：

- 覆盖核心功能
- 可测试
- 可观察
- 不歧义
- 与业务规则一致
- 包含重要异常和限制条件

常见问题：

- 验收标准过于空泛
- 只是重复功能描述
- 缺少失败场景和权限场景

## 16. 风险与待确认项检查

检查是否集中列出：

- 待业务确认项
- 接口待确认项
- 历史数据处理待确认项
- 合规 / 法务 / 风控相关风险
- 上线依赖和排期风险

常见问题：

- 假设写进正文，像既定事实
- 风险散落各处，不方便评审收口
- 真正影响开发的待确认项没有集中列出

## 高频漏项提醒

以下内容最容易漏：

- 角色差异
- 数据权限
- 状态流转
- 删除 / 编辑限制
- 提示文案
- 超时和并发
- 批量操作规则
- 导入导出规则
- 日志与报表口径
- 验收标准
- 待确认项

## 常见冲突模式

重点检查这些冲突：

- 背景与目标不一致
- 目标与功能清单不一致
- 页面操作与业务规则冲突
- 字段定义与校验规则冲突
- 权限说明与页面说明冲突
- 验收标准与正文逻辑冲突
- 状态名称前后不一致

发现冲突时，不要模糊带过，应直接指出。

## 推荐评审输出格式

评审现有 PRD 时，优先按以下格式输出：

### 已明确项
已经足够清楚、可直接推进的部分。

### 缺失项
完全没写，但研发、设计、测试一定会问的内容。

### 模糊项
虽然写了，但粒度不足、容易产生不同理解的内容。

### 冲突项
前后矛盾、规则打架、术语不一致的内容。

### 风险点
可能造成返工、延期、上线问题的风险。

### 待确认项
需要业务方、产品负责人、研发负责人拍板确认的事项。

### 修改建议
给出具体补法，不只指出问题。

## 优先级建议

需要时对问题标注优先级：

- P0：阻塞评审、阻塞开发、阻塞测试
- P1：重要问题，不解决可能造成返工
- P2：优化项，提升表达清晰度

## 评审会前最后一问

在文档准备进入正式评审前，最后自问：

- 业务方是否能看懂为什么做
- 研发是否能看懂怎么做
- 测试是否能看懂怎么验
- 文档里是否还有会场上一定会被追问的问题

如果答案是否定的，说明文档还没准备好。
