# 阶段一与阶段二章节结构参考

## 用途

本文件用于承接 `prd-maker` 中阶段一与阶段二的默认章节结构说明。

## 何时读取

优先在以下情况读取本文件：

- 用户当前处于阶段一：需求分析 / 简版 PRD 骨架
- 用户当前处于阶段二：细化功能清单 / 端口功能补齐
- 需要确定 `XXX-需求文档.md` 的默认章节结构
- 需要判断阶段一与阶段二的章节差异和填写深度

以下情况不优先读取本文件：

- 已明确进入阶段三，需要制作详细方案
- 只需要补充详细设计正文模板或附录页面规格
- 只需要做 PRD review 输出

适用于以下场景：

- 阶段一：需求分析 / 简版 PRD 骨架
- 阶段二：细化功能清单 / 端口功能补齐

目标是在不改变主 Skill 阶段规则的前提下，将阶段一、阶段二的默认文档结构沉淀到可按需读取的参考文件中。

## 阶段一默认输出：简版 PRD 骨架

如果用户还在前期沟通阶段，默认先输出：

0. 文档信息（按需）
1. 需求概述
   1.1 需求背景
   1.2 需求目标
2. 角色说明
   2.1 角色说明
   2.2 用户故事
3. 范围说明
4. 业务流程
5. 功能清单 / 功能结构
6. 关键规则补充
7. 风险与待确认项

这一版的目标是让团队先快速达成方向一致，不强求一次写全。

其中功能清单默认只写到模块和核心功能点，不展开为完整端口级功能列表。

## 阶段二默认输出：按端口补齐的功能清单

当用户明确要求继续细化功能清单，或已经有简版骨架可继续展开时，优先在 `XXX-需求文档.md` 中补齐：

0. 文档信息（按需）
1. 需求概述
   1.1 需求背景
   1.2 需求目标
2. 角色说明
   2.1 角色说明
   2.2 用户故事
3. 范围说明
4. 业务流程
5. 功能清单 / 功能结构
6. 关键规则补充
7. 风险与待确认项

这一阶段的重点是把功能清单按端口和模块补齐到完整、可评审，章节结构与阶段一保持一致，只是补充深度更高，仍然不直接下钻到页面字段级设计。

## 默认文档风格

更贴近国内产品经理常见 PRD 风格，优先使用这些章节：

#### 0. 文档信息（按需）
可包含：文档名称、版本号、作者、评审人、更新时间、更新记录、关联项目、原型链接。

#### 0.1 更新记录 / 版本记录（按需）

对于会持续多轮迭代的 PRD，建议在文档前部保留本节，用于沉淀修改轨迹。

建议至少记录：

- 更新时间
- 版本号或回合编号
- 本轮修改章节
- 修改摘要
- 待确认项是否新增、关闭或变更

已确认或已关闭的待确认项，默认不要继续保留在“风险与待确认项”正文列表中；如需保留处理痕迹，建议仅在 `更新记录` / `版本记录` 中体现。

推荐使用 Markdown 表格，保持简洁即可，例如：

| 日期 | 版本/回合 | 变更章节 | 修改摘要 | 备注 |
| --- | --- | --- | --- | --- |
| 2026-04-03 | v0.2 | 背景、功能清单 | 补充目标用户与核心流程 | 新增 2 个待确认项 |

如果用户已有公司模板中的版本记录格式，优先沿用原格式。

#### 1. 需求概述
用 3-5 句话先说明这是什么需求、解决什么问题、涉及哪些角色、最终希望达到什么结果。

##### 1.1 需求背景
写清楚现状、痛点、触发原因和业务动因。

##### 1.2 需求目标
写清楚上线后预期改变什么，必要时给出指标口径。

#### 2. 角色说明

##### 2.1 角色说明
按角色拆分可见范围、可操作范围、数据范围。

##### 2.2 用户故事
在角色说明之后补充关键用户故事，优先写明“谁，在什么场景下，为了什么目标，需要什么能力”。

#### 3. 范围说明
明确本期范围、非本期范围、后续规划。

#### 4. 业务流程
优先按步骤编号书写；有状态流转时写清楚状态变化。

#### 5. 功能清单 / 功能结构
先总后分，先模块后页面。

当使用表格呈现功能清单时，默认优先按“一个模块一行”组织内容。

推荐写法：

| 模块 | 核心功能点 |
| --- | --- |
| 车位管理 | 车位信息录入、车位状态管理、车位上下架、车位定价配置 |

不推荐写法：

| 模块 | 核心功能点 |
| --- | --- |
| 车位管理 | 车位信息录入、车位状态管理 |
| 车位管理 | 车位上下架、车位定价配置 |

如同一模块下功能点较多，可使用顿号、分号或 `<br>` 在单元格内分隔，但应尽量避免重复书写同一个模块名。

阶段一和阶段二默认都使用以上 0-7 的章节结构推进，只是阶段二会把第 5 章补齐到按端口划分的完整功能列表。

#### 6. 关键规则补充
集中补充状态规则、限制规则、时效规则、校验口径、异常口径、权限口径等关键规则。

如项目存在国产化 / 信创要求，也应在本节补充相关适配内容，例如：

- 是否要求兼容国产操作系统
- 是否要求兼容国产数据库、中间件、浏览器或办公环境
- 是否存在信创环境下的部署限制、接口限制或组件替代要求
- 是否需要对第三方依赖、文件预览、打印、加密、签章等能力做国产化适配说明

#### 7. 风险与待确认项
最后集中列出未定事项，不要把不确定内容藏在正文里。

如果某条待确认项已经确认、关闭或不再构成风险，默认应从本节移除，不继续保留为“已关闭事项”列表。
