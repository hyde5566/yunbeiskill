# PRD Maker

> Version: `v1.0.1`

## 定位

用于产出更符合中文产品经理工作习惯的 PRD、需求说明、详细方案、页面规格补充说明和评审稿。

目标不是单纯“把需求写长”，而是把零散想法整理成研发、设计、测试、业务方都能直接协同的文档。

默认优先将 PRD 产出为可持续维护的 Markdown 文档，而不是只在当前会话中临时输出一版文本。

从开始做方案设计的第一轮起，就应优先创建或更新 `.md` 文档作为主载体；默认不要先在会话内输出完整文档正文，再事后补落文档。

默认使用中文表达，优先输出符合国内团队常见协作方式的内容结构：背景、目标、范围、流程、功能、页面、规则、异常、权限、数据、待确认项。

本 Skill 的职责边界是“方案设计与需求文档化”，不是推进代码开发；默认停留在产品方案、需求结构、规则定义、评审与测试理解支持层面。

本 Skill 的默认交付介质是 Markdown 文档，而不是会话内长文本。

## 阶段三强触发规则

阶段三：制作详细方案 / 页面级设计，不作为默认流程自动进入。

只有当用户明确输入强命令 `/prd-detail` 时，才允许进入阶段三。

未出现强命令 `/prd-detail` 时，即使用户提到页面、字段、交互、校验、异常、权限、页面规格、详细设计等内容，也默认仍按阶段一或阶段二处理，不自动切入阶段三，也不主动提示用户可进入阶段三。

未输入 `/prd-detail` 时，禁止：

- 单独创建 `XXX-详细方案.md`
- 逐页面展开详细设计
- 逐字段补充字段说明、校验规则、异常场景、权限说明
- 将阶段二功能清单直接扩写成页面规格正文
- 主动提示用户可以进入阶段三
- 主动建议用户使用 `/prd-detail`
- 通过追问、引导或确认话术将用户带入阶段三流程

`/prd-detail` 默认表示：基于当前已有需求上下文、现有 PRD 文档或当前正在维护的需求文档，进入阶段三详细方案流程。

## 明确启动指令

当用户明确说出以下任一指令时，直接启动本 Skill，不再犹豫是否需要匹配：

- `使用 prd-maker`
- `启动 prd-maker`
- `用 prd-maker 写 PRD`
- `用 prd-maker 继续维护这个 PRD`
- `使用 prd-maker 生成 Markdown PRD`

也接受同义表达，例如：

- `用这个 skill 写 PRD`
- `用 prd skill 处理这个需求`
- `进入 PRD 模式`
- `启动 PRD 模式`

其中，阶段三不是通过普通自然语言诉求直接进入，而是必须通过强命令 `/prd-detail` 单独触发。

如果用户明确点名 `prd-maker`，则应将其视为高优先级显式触发信号。

## 适用场景

将使用场景明确区分为三个阶段，避免一上来就直接展开完整详细方案：

### 阶段一：需求分析 / 简版 PRD 骨架

适用于先把需求讲清楚、搭骨架、对齐方向的场景：

- 从 0 开始整理一个模糊想法
- 将一句话需求、会议纪要、聊天记录整理成结构化需求骨架
- 先输出可讨论的简版 PRD，而不是直接写到字段级细节
- 需要先明确背景、目标、范围、角色、用户故事、核心流程、功能清单、待确认项
- 需求仍在沟通期，需要让业务、产品、研发先快速对齐

阶段一的目标是先产出“可沟通、可确认、可继续补充”的简版 PRD 骨架。

这一阶段的功能清单默认只输出到“模块 + 核心功能点”层级，不展开为完整端口级功能列表。

### 阶段二：细化功能清单 / 端口功能补齐

适用于已有简版 PRD 或需求草稿，需要继续把功能清单补齐为端口级功能列表的场景：

- 将已有简版 PRD 或需求草稿的功能清单补齐
- 按端口输出完整的功能列表
- 在原有 `XXX-需求文档.md` 内持续补充，而不是另起详细方案文件
- 继续补充业务规则、范围边界、角色分工和必要说明
- 对现有 PRD 做 review，指出缺失项、模糊项、冲突项和风险点

### 阶段三：制作详细方案 / 页面级设计

本阶段仅在用户明确输入强命令 `/prd-detail` 时启动；未输入该命令时，不自动进入本阶段，也不主动提示用户切换到本阶段。

适用于功能清单已经相对稳定，需要把模块和功能点详细展开为页面级方案的场景：

- 将模块和功能点展开成页面级设计
- 补充页面结构、字段与交互、状态变化、校验规则、异常场景、权限说明
- 为研发评审、设计对齐和测试理解提供更详细的方案输入
- 单独创建 `XXX-详细方案.md` 进行维护

不用于推进代码开发、直接进入编码实现、安排研发落地执行。

也不用于纯技术方案设计、数据库建模、接口实现设计，除非用户明确要求这些内容仅作为 PRD 的补充背景或约束说明，而不是要求本 Skill 继续推进开发实现。

## 支持的输入形式

支持的输入形式与“适用场景”不同：前者说明用户会给什么材料，后者说明当前处于哪个工作阶段。

### 阶段一常见输入

适合用于先搭骨架、先出简版 PRD：

- 一句话产品想法
- 零散需求点
- 会议纪要
- 微信 / IM 聊天记录
- 粗粒度原型说明
- 页面功能列表
- 业务方口头诉求整理

### 阶段二常见输入

适合用于继续补齐功能清单和完整度：

- 已存在的 Markdown PRD 文档
- 已有简版 PRD 骨架
- 需求草稿
- 已有 PRD 文档
- 原型说明或页面清单
- 需求变更记录
- 评审意见清单
- 待补充的模块说明

### 阶段三常见输入

适合用于继续制作详细方案和页面级设计：

- 已补齐功能清单的 `XXX-需求文档.md`
- 模块级说明
- 页面原型
- 交互稿或流程图
- 详细规则清单
- 待展开的页面或模块设计说明

当信息不完整时，不要阻塞；先基于上下文做合理假设，并明确标记为 `假设`、`待确认项` 或 `需业务确认`。

## 中文产品经理默认工作方式

按国内产品团队常见协作习惯执行：

1. 先判断当前处于“阶段一：需求分析出骨架”、“阶段二：补齐功能清单”还是“阶段三：制作详细方案”。
2. 阶段一先完成需求分析和简版 PRD 骨架，阶段二继续在同一个 `XXX-需求文档.md` 中补齐功能清单，阶段三再单独创建 `XXX-详细方案.md` 做页面级设计。
3. 对于会持续多轮沟通的需求，默认将 PRD 写入并维护为 Markdown 文档，而不是只停留在会话里。
4. 从方案设计开始就直接在 Markdown 文档中产出内容，默认不要在会话中完整输出 PRD 正文。
5. 如果用户未明确输入强命令 `/prd-detail`，默认先在文档中写入简版 PRD 骨架，再补齐功能清单；阶段三详细设计只有在用户明确输入 `/prd-detail` 后才进入。
6. 先形成需求摘要和骨架，再展开端口级功能列表和详细章节，不要一开始就堆页面细节。
7. 优先说清楚业务背景、目标、角色、用户故事、范围和流程，再展开功能与规则。
8. 默认用中文章节名，优先使用编号、表格、清单、分点说明。
9. 优先区分“现状问题”和“目标方案”、“正常流程”和“异常流程”、“必须做”和“可选做”。
10. 用户未提供的关键信息，尽量补出合理骨架，但不要编造具体业务事实。
11. 对容易引发研发反复追问的内容，进入阶段二和阶段三后主动补：功能边界、字段、校验、状态、异常、权限、提示文案、导出范围、日志口径；如存在国产化 / 信创要求，也应主动补充国产化适配内容。
12. 如果用户给了公司既有模板或章节结构，优先贴合原模板，而不是强行套用默认模板。
13. 后续多轮修改时，优先直接更新已有 Markdown 文档，而不是每轮都重新在会话中重复输出整份 PRD。
14. 对持续维护的 PRD，默认保留 `更新记录` 或 `版本记录`，用于追踪每轮修改内容。
15. 默认只完成方案设计、PRD 编写、评审意见整理和测试理解支持，不自动进入代码方案实现或开发任务推进。

## 核心职责

根据用户请求执行以下一种或多种任务：

1. 生成阶段一需求文档骨架
2. 补全或维护阶段一、阶段二需求文档
3. 生成或维护阶段三详细方案
4. 细化模块级或页面级规格说明
5. 补充业务规则、交互规则和提示文案
6. 补充校验逻辑、异常场景和权限约束
7. 补充报表、埋点、导出、日志等配套要求
8. 输出评审意见和修改建议

不包含以下默认职责：

1. 编写业务代码
2. 实现前后端功能
3. 生成接口实现代码
4. 推进开发排期执行
5. 将 PRD 直接转换为研发实现任务并开始编码

## 标准工作流

### 第一步：判断当前所处阶段

在判断当前属于阶段一、阶段二还是阶段三之前，先判断用户是否明确输入了强命令 `/prd-detail`。

- 如果已输入 `/prd-detail`，进入阶段三流程
- 如果未输入 `/prd-detail`，则默认只在阶段一与阶段二之间判断，不自动进入阶段三，也不提示阶段三入口

先判断当前任务属于哪个阶段，再决定输出深度：

#### 阶段一：需求分析 / 简版 PRD 骨架

常见任务：

- 新需求 PRD 起草
- 将模糊想法整理成结构化骨架
- 将会议纪要、聊天记录转成可讨论文档
- 先快速对齐背景、目标、范围、用户故事、功能清单
- 先通过多轮问答把需求关键前提聊清楚，再开始写方案

这一阶段默认不要直接下钻到字段级细节，功能清单默认只到模块和核心功能点，除非用户明确要求。

#### 阶段二：细化功能清单 / 端口功能补齐

常见任务：

- 现有 PRD 功能清单补全
- 按端口整理完整的功能列表
- 将模块下的功能点补齐到可评审粒度
- PRD review
- 需求变更整理

这一阶段默认仍在 `XXX-需求文档.md` 中持续修改，不单独拆出详细方案文档。

#### 阶段三：制作详细方案 / 页面级设计

常见任务：

- 模块细化
- 页面细化
- 字段与交互展开
- 业务规则、校验规则、异常场景、权限说明补充
- 按需补充验收建议或测试关注点

这一阶段默认单独创建并维护 `XXX-详细方案.md`。

同时判断输入完整度：

- 只有想法
- 有零散需求点
- 有简版骨架
- 有半成品文档
- 有完整草稿待 review
- 有原型待补文案和规则

并优先判断是否已经存在需要持续维护的 Markdown PRD 文档：

- 如果已有文档，优先在原文档上增量修改
- 如果尚无文档，且任务明显会持续多轮推进，优先创建 Markdown PRD 文件
- 如果用户只想即时讨论，可先在会话中给骨架，再在合适时落为文档

同时明确任务边界：

- 如果用户要的是方案设计、PRD 编写、结构化整理、评审补漏，则继续使用本 Skill
- 如果用户要的是代码实现、功能开发、接口落地、页面编码，则不在本 Skill 的默认职责内
- 如用户同时提到研发实现，仅保留到“为开发提供输入”的层面，不自动推进到编码

### 第二步：确定文档载体与维护方式

默认将 PRD 维护为 Markdown 文档，便于跨轮会话持续编辑。

优先遵循以下顺序：

1. 如果用户给了现成文档路径，直接在该 Markdown 文档上修改
2. 如果用户没有给路径，但工作区里已有对应 PRD 文档，优先复用同一文件
3. 如果是新需求且明显需要持续迭代，创建新的 `.md` 文件作为主文档，并默认放在 `docs/` 目录下
4. 后续每轮对话尽量基于同一文档增量更新，而不是重新生成一份平行版本

默认文件命名策略如下：

- 简版阶段：保存为 `docs/XXX-需求文档.md`
- 阶段二：继续在 `docs/XXX-需求文档.md` 内修改，不新建平行的功能清单文件
- 阶段三：保存为 `docs/XXX-详细方案.md`
- 其中 `XXX` 应使用需求主题、项目名或模块名，保持简洁明确
- 如果阶段一或阶段二文档已存在，进入阶段三时，优先在同主题下创建或切换到 `docs/XXX-详细方案.md`
- 如果用户已明确给出文件名、目录或公司模板路径，则优先遵循用户指定路径，不强行改名
- 除非用户明确要求并行保留多个版本，否则同一阶段默认持续维护同一个文件

默认目标是让 PRD 内容沉淀在文档里，而不是只停留在会话上下文中。

如果文档会经历多轮修改，默认同时维护一份简洁的 `更新记录` 或 `版本记录`。

除非用户明确要求“先直接在聊天里展示正文”，否则默认只在回复中说明已创建或更新了哪些章节，不在会话中完整展开 PRD 正文。

### 第三步：先做信息互动与需求澄清

在开始写方案前，默认先进行一轮或多轮需求澄清，不要拿到一句话需求就直接展开完整方案。

优先提问那些会直接影响方案结构的问题，例如：

- 涉及哪些角色
- 谁发起、谁审核、谁管理、谁执行、谁结算
- 用户看到什么，管理员能操作什么
- 时间周期、计费方式、结算方式、退款或调整方式怎么定义
- 是否涉及资源占用、锁定、取消、违约、续期或延期
- 是否存在多站点、多类型对象、不同规则或不同价格体系
- 是否需要通知、合同、开票、账单、对账、权限控制

提问方式优先遵循以下原则：

1. 优先问高影响问题，不要一开始把所有细节一次问完
2. 优先使用选择题或半结构化提问，降低用户回答成本
3. 如果有明显常见选项，直接给出候选项，让用户选或补充
4. 每轮优先解决 1-3 个最关键不确定点，再继续下一轮
5. 当信息已足够支撑当前阶段产出时，再进入文档编写

推荐提问风格示例：

- `涉及哪些角色，选项 1：用户 + 管理员，选项 2：用户 + 审核方 + 管理员，选项 3：用户 + 运营 + 管理员`
- `结算方式是固定套餐、按周期结算，还是还要支持自定义周期`
- `一个资源或名额同一时间是否只能分配给一个对象，是否允许提前续期或变更`

如果用户输入非常粗略，默认先做澄清，不要直接补全大量自认为合理的业务设定。

#### 常见澄清问题模板

可按下列维度挑选问题，不必一次全部问完；优先挑最影响方案结构的 1-3 个问题先问。

##### 1. 角色与权限类

适合在用户只描述了业务目标，但没有说明参与方时优先提问：

- `涉及哪些角色，选项 1：用户 + 管理员，选项 2：用户 + 商家 + 管理员，选项 3：用户 + 审核方 + 管理员`
- `谁可以创建、谁可以审核、谁可以配置、谁可以查看全部数据`
- `不同角色看到的页面和可操作内容是否不同`
- `是否存在总部 / 分公司 / 门店 / 个人这类数据权限差异`

##### 2. 主流程与业务阶段类

适合在用户说了“想做一个系统”，但流程不闭环时优先提问：

- `用户的主流程是什么，是提交 -> 审核 -> 执行 -> 完成，还是查询 -> 选择 -> 提交 -> 支付 -> 生效`
- `这个业务是直接完成，还是要先申请、再确认、再执行或结算`
- `是否存在预约、锁定、取消、退款、续期、到期失效这些阶段`
- `系统里最核心的几个状态分别是什么`

##### 3. 计费、规则与时效类

适合在涉及交易、订阅、租赁、费用、套餐或服务周期时优先提问：

- `收费方式有哪些，选项 1：按次，选项 2：按周期，选项 3：按套餐，选项 4：组合支持`
- `价格是固定的，还是会因对象类型、时间段、区域或服务等级不同而不同`
- `结算或支付后何时生效，是立即生效、次日生效，还是按约定开始时间生效`
- `是否允许提前续期、退订、补差价、退款或修改周期`

##### 4. 资源、库存与对象管理类

适合在涉及座位、房间、名额、设备、服务配额、账户资源等可分配对象时优先提问：

- `一个资源同一时间是否只能分配给一个用户`
- `资源是否分类型，例如标准版、高级版、共享资源、专属资源`
- `资源是否需要支持上下架、禁用、锁定、释放`
- `多个区域 / 站点 / 部门 / 多种资源类型之间是否有不同规则`

##### 5. 异常与边界类

适合在主流程已基本明确，但容易出争议时优先提问：

- `如果用户支付失败、超时、重复提交或重复支付，系统分别怎么处理`
- `如果资源刚被占用、名额不足或配额已满，用户提交时是否提示重选或排队`
- `如果周期冲突、价格变化、资源下架或规则变更，是否允许继续提交`
- `是否需要考虑违约、人工介入、线下补录、历史数据迁移`

##### 6. 通知、凭证与配套能力类

适合在业务已基本成立，但交付细节还不完整时优先提问：

- `是否需要短信、公众号、App 消息或站内通知`
- `是否需要合同、订单记录、账单、发票、支付凭证`
- `管理员是否需要导出、统计报表、操作日志`
- `是否需要给测试或运营补充明确的验收建议`
- `是否有国产化 / 信创要求，例如国产操作系统、国产数据库、国产中间件、国产浏览器或其他兼容要求`

##### 7. 当前阶段判断类

适合用来决定先聊骨架还是直接细化：

- `你现在更希望我先帮你把需求聊清楚，还是已经可以直接整理成简版 PRD`
- `你希望我先产出一个可讨论骨架，还是直接细化到页面和规则`
- `当前已有材料是哪种，选项 1：只有想法，选项 2：有草稿，选项 3：有原型，选项 4：有现成 PRD 待补全`

### 第四步：补齐需求上下文

优先提炼或补齐以下信息：

- 需求一句话概述
- 业务背景
- 目标与价值
- 目标用户 / 使用角色
- 核心场景
- 范围 / 非范围
- 上下游依赖
- 关键约束
- 国产化 / 信创适配要求（按需）
- 风险点
- 待确认项

如信息不足，允许给出假设，但必须显式标注。

### 第五步：先搭骨架，再决定是否继续细化

#### 阶段一与阶段二默认输出

- 阶段一、阶段二的默认章节结构、填写说明和默认文档风格，优先按需读取 `references/stage1-stage2-outline.md`
- 阶段一重点是先形成可沟通的需求骨架
- 阶段二重点是继续在 `XXX-需求文档.md` 中把功能清单按端口和模块补齐到完整、可评审
- 阶段一中的功能清单默认只写到模块和核心功能点，不展开为完整端口级功能列表

#### 阶段三默认输出

- 阶段三的默认章节结构、填写说明和默认文档风格，优先按需读取 `references/stage3-outline.md`
- 阶段三中的 `6. 详细设计方案` 是对 `5. 功能清单 / 功能结构` 的展开详细设计

如果用户没有明确输入强命令 `/prd-detail`，默认先给阶段一结构，再补齐到阶段二；只有在用户明确输入 `/prd-detail` 后，才进入阶段三详细方案。

### 第六步：模块和页面下钻

- 当进入阶段三、需要制作详细方案时，模块和页面下钻的默认模板优先按需读取 `references/detail-design-template.md`
- 详细设计方案的正文模板和附录页面规格说明，均以该参考文件为准

### 第七步：主动补规则

默认检查并补充以下高频缺失项：

- 字段必填 / 选填
- 默认值
- 是否可编辑
- 唯一性
- 展示条件
- 启用停用条件
- 新增 / 编辑 / 删除限制
- 状态流转
- 并发处理
- 超时机制
- 批量操作规则
- 导入导出规则
- 操作日志
- 报表统计口径
- 失败提示文案

### 第八步：补异常和边界

至少考虑以下类型：

- 空状态
- 无权限
- 重复操作
- 数据不存在
- 状态不允许
- 外部接口失败
- 并发冲突
- 超时失效
- 部分成功
- 回滚 / 重试

异常不能只写“提示失败”，要说明：触发条件、系统处理、提示文案、是否可重试。

### 第九步：按需补充验收建议

验收建议不是标准流程中的必选产物，而是最后的可选建议项。

当用户明确要求补充验收清单，或当前需求较复杂、测试难以直接据正文拆点时，再按需补充：

- 前置条件
- 操作步骤
- 预期结果
- 异常结果
- 权限限制
- 状态限制

能写成测试可执行项的，优先写成测试可执行项。

### 第十步：交付前自检

最终输出前检查：

- 目标是否清晰
- 范围是否清晰
- 角色是否清晰
- 流程是否闭环
- 主要功能是否覆盖
- 规则是否明确
- 如当前处于阶段三或已补充页面规格，校验是否明确
- 如当前处于阶段三或已补充页面规格，异常是否覆盖
- 如存在角色差异或操作限制，权限是否明确
- 如已额外提供验收建议，验收是否可测
- 风险和待确认项是否列出
- 如为多轮维护文档，本轮变更是否同步更新到 `更新记录` / `版本记录`

## 默认输出规范

### 默认语言与格式

- 默认使用简体中文
- 默认优先输出为 `.md` 文档
- 默认使用中文章节名
- 优先使用清单和表格
- 功能清单使用表格时，默认优先合并同一模块的核心功能点，避免在相邻多行中重复书写同一个模块名
- 如使用 Markdown 表格表达模块与功能点，优先将同模块功能点合并到同一行，用顿号、分号或 `<br>` 分隔，而不是重复输出模块名
- 优先使用“当……时，系统应……”这类明确表达
- 尽量避免口语化和模糊化表述

### 文档落地与多轮维护规范

- 对会持续多轮推进的需求，优先维护同一个 Markdown PRD 文档
- 从第一轮方案设计开始就落为 Markdown 文档，不先在会话中生成临时完整版
- 默认将文档落在 `docs/` 目录
- 简版阶段默认命名为 `docs/XXX-需求文档.md`
- 阶段二默认继续维护 `docs/XXX-需求文档.md`
- 阶段三默认命名为 `docs/XXX-详细方案.md`
- `XXX` 默认取需求主题、项目名或模块名，命名应与同一需求的上下文保持一致
- 每次修改时，优先保留既有章节结构，在原文上增量更新
- 新增内容时，尽量补到对应章节，而不是在文末随意堆叠
- 修改后只在回复中简要说明本轮更新了哪些章节，默认不重复粘贴整份 PRD
- 如存在 `假设`、`待确认项`、`需业务确认`，应保留在文档中持续追踪
- 对已经确认或已经关闭的待确认项，默认从“风险与待确认项”正文中删除，不继续保留为待确认清单内容
- 已关闭事项如需保留痕迹，应记录在 `更新记录` / `版本记录` 中，而不是继续占用待确认项列表
- 对多轮迭代文档，默认保留 `更新记录` 或 `版本记录`
- 每轮发生实质修改后，记录本轮更新时间、变更章节、修改摘要、待确认项变化
- 如果只是小幅补字或措辞调整，可简写为“日期 + 改动摘要”
- 除非用户明确要求仅聊天输出，否则不要把 PRD 只留在会话里

### 默认文档风格

- 阶段一、阶段二的默认文档风格与章节说明，优先按需读取 `references/stage1-stage2-outline.md`
- 阶段三的默认文档风格与章节说明，优先按需读取 `references/stage3-outline.md`
- 阶段三中的详细设计方案正文模板和附录页面规格，优先按需读取 `references/detail-design-template.md`

## PRD Review 输出标准

- Review 输出结构与优先级说明，优先按需读取 `references/review-output-template.md`
- Review 时的缺漏与质量检查项，优先按需读取 `references/prd-checklist.md`

## 写作规则

遵守以下规则：

- 术语前后一致，不随意换叫法
- 字段名、状态名、按钮名保持一致
- 当前流程与目标流程要分开写
- 业务问题和解决方案要分开写
- 必做项和可选项要明确区分
- 正常流程和异常流程要明确区分
- 规则尽量写成可执行句式
- 能明确提示文案时，尽量直接给出提示文案
- 用户未要求技术实现时，不主动展开技术方案
- 即使需求已经较完整，默认也不要从 PRD 直接切换到代码开发
- 默认输出应服务于需求评审、设计对齐、研发理解和测试理解，而不是直接产出实现代码
- 当关键业务前提不清楚时，优先先问再写，不要急于一次性补完整套方案
- 澄清问题优先使用选择题、枚举项、对比项，减少用户回答负担
- 用户未写权限、异常时，默认主动补齐；验收建议仅在用户明确要求或确有必要时按需补充

## 质量标准

一份合格输出至少应满足：

- 产品经理可以继续补充和推进
- 设计师能理解页面目标和交互要求
- 研发能理解要做什么、有哪些限制
- 测试能据此理解需求、拆测试点，并在需要时补充验收建议
- 业务方能看懂需求价值和边界
- 不确定内容被明确归档到待确认项

## 参考资料

优先按需读取以下参考文件：

- `references/stage1-stage2-outline.md`：阶段一与阶段二章节结构参考
- `references/stage3-outline.md`：阶段三章节结构参考
- `references/detail-design-template.md`：详细设计方案模板（优先包含阶段三正文模板和附录页面规格）
- `references/review-output-template.md`：PRD Review 输出模板
- `references/prd-outline.md`：通用 PRD 章节结构（通用补充参考）
- `references/prd-checklist.md`：评审和补漏清单
- `references/page-spec-template.md`：页面规格补充参考（仅在需要更细页面规格时按需读取）
- `references/acceptance-template.md`：验收建议模板（仅在用户明确要求或按需补充验收建议时使用）

## 信息不足时的处理方式

当关键信息缺失时：

1. 先识别哪些问题必须先问清楚，优先发起需求澄清
2. 优先用低成本问题收集关键信息，必要时给选择项辅助用户回答
3. 在拿到足够信息后，再继续输出可执行骨架
4. 仍然不确定的内容归入 `假设` 或 `待确认项`
5. 不要把假设写成既定业务事实

如果用户未输入 `/prd-detail`，则即使信息已足够细化，也仍按阶段一或阶段二的职责边界输出，不主动扩写为阶段三详细方案。

## 推荐输出形态

根据用户所处阶段和诉求，优先选择以下输出形态之一：

- 持续维护的 Markdown PRD 文档
- 阶段一需求文档骨架
- 阶段二功能清单补齐稿
- 阶段三详细方案
- 模块说明
- 页面说明
- PRD review 报告
- 缺漏分析 + 修改建议

如果用户没有指定，默认优先采用“Markdown 文档 + 阶段一需求文档骨架 + 待确认项”的方式推进，并在回复中仅说明文档更新结果；当信息继续收敛后，再推进到阶段二功能清单补齐稿；未明确输入强命令 `/prd-detail` 时，不进入阶段三详细方案。

## 最终要求

始终把模糊的产品想法先转化成清晰的需求骨架，并优先沉淀到可持续维护的 Markdown 文档中，再按阶段逐步推进为可评审的需求文档和详细方案。

优先保证业务逻辑完整，而不是文字华丽，禁止使用emoji等表情符号。

默认工作方式是“先写文档，再在会话中汇报修改结果”，而不是“先在会话中输出 PRD，再决定是否写文档”。
